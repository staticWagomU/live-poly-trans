# レーン間の厳密な同期

Step 4の最後の項目。録音3ファイルとトランスクリプトの時間軸を、OSが付けるキャプチャ時刻に基づいて合わせる。

## 現状の何が問題か

いまレーンの位置決めは「先行レーンを時計とみなし、0.5秒（mixのlag）以上遅れたら無音期間だったとみなす」という推測で成り立っている。

- レーンの開始オフセットは `start_capture()` が返るまでの経過時間（`Instant::elapsed`）で代用している。実際にタップが最初のサンプルを受け取った時刻ではない（タップは再生が始まるまで1コールバックも来ない）
- 0.5秒未満の遅れは「バッファリング」として詰めて置かれる。デコード中は両レーンともpumpされないため、レーン間の到着時刻が最大1〜2秒ずれることがあり、その分だけ音が後ろに寄る
- リングバッファ溢れ（overrun）で落ちたサンプルは、時間軸上の穴ではなく「詰め」として扱われ、それ以降が前にずれる

## 使えるもの（調査済み）

macOSでは両レーンの時刻が**同じmach host time**で取れる。

| レーン | 取得元 | 備考 |
|---|---|---|
| マイク | cpal `InputCallbackInfo::timestamp().capture` → `as_nanos()` | mHostTimeを入力レイテンシ分だけ戻した値 |
| スピーカー | Process TapのIOProcが受け取る `in_time.mHostTime` | machティック。`mach_timebase_info` でnsへ |

`libc`（macOSのみ）に `mach_timebase_info` / `mach_absolute_time` があり、Cargo.lockに既に入っている。

Windows（WASAPI）を足すときは、cpalがそのプラットフォームで使う時計に合わせる必要がある。この前提はコードにコメントで残す。

## 設計

### 1. キャプチャがアンカーを流す

```rust
/// あるコールバックの先頭フレームが、いつ録られたか。
pub struct Anchor { pub frame: u64, pub nanos: u64 }
```

`CaptureSession` に `times: rtrb::Consumer<Anchor>` を追加。コールバックは**実際にリングへ書けたフレーム数**を累積して `frame` とするので、overrunで落ちた分は時間の穴として現れる（＝あるべき姿）。

### 2. パイプラインが絶対位置を計算する

消費側は読み出した累積フレーム `F` に対し、`F` 以下で最新のアンカーを引き、
`nanos(F) = anchor.nanos + (F - anchor.frame) / rate` で時刻を出す。

セッションのゼロ点＝最初にアンカーを出したレーンの先頭サンプル（実質マイクの1サンプル目）。

### 3. ミキサーとレコーダは位置を受け取るだけにする

- `Mixer::push_at(lane, samples, at)` — カーソル推測をやめ、絶対位置で加算
- `SessionRecorder::write_at(lane, samples, at)` — `at` までを無音で埋めてから書く
- `LaneSpec.start_offset` は不要になる（位置が絶対値になるため）
- `MIX_LAG` はデコード滞留（最大1〜2秒）を吸収できるよう2秒へ。lagは順序合わせのためだけになり、位置決めには効かない

### 4. トランスクリプトの時刻

`LaneTimeline` は残すが、入力を「レコーダのパディング量」から「そのチャンクの録音位置 − ストリーム位置」に変える。録音していないときも時刻が正しくなる。

## 検証

ユニットテストに加えて、**音響結合を使った実測**を行う:

1. ヘッドホンを外し、内蔵スピーカーで音（拍手・ビープなど立ち上がりの鋭い音）を再生しながらマイクを開けて録音
2. `scripts/check-recording.py --sync` で mic.wav と speaker.wav の包絡線を相互相関

期待値: ピークが数ms〜30ms程度（空気の伝搬＋入力レイテンシ）で、かつ録音のたびに安定していること。現状の実装だと開始タイミング次第で数百msの幅で動くはず。

## 実測結果（2026-08-19, M4 Pro / 内蔵スピーカー・内蔵マイク）

`afplay Ping.aiff` を3.5秒間隔で6回鳴らし、その間は無音で40秒録音。

- 全体のオンセット相互相関: **+15ms**（スコア0.344 / 他ラグ0.064、5.4倍のコントラスト）
- クリック単位の局所相関: 3〜6発目が **+16 / +16 / +15 / +15 ms**。18.5秒離れた2点で1ms以内なので、この区間ではドリフトなし
- 1〜2発目は測定不能。マイク側の音量がノイズフロアを下回っていた（0.6倍・0.9倍）ため。3発目以降は1.5〜1.7倍で、スコアの差もはっきり出ている

残る15msは固定の遅延（スピーカー→マイクの空気伝搬＋OSが申告しきらない入力レイテンシ）で、ソフト側のズレやドリフトではない。トランスクリプトの位置決めにも聴感にも影響しない範囲なので、定数で引くような補正はしない（機種依存の当て推量になる）。

次に測るときはクリックの音量を上げること。今回はマイク側のSNRが足りず、6発中2発を落とした。
